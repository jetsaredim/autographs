# PR #294 contract revision review

## ISSUES FOUND

**Verdict:** The pointer-first/shared-media/tombstone design addresses the two round-2 findings in principle, but the deployment and live-proof requirements are not yet executable as written. Keep convergence at `reassessment_required` until these properties are covered and independently rechecked.

### Findings

1. **BLOCKER — The cutover must prevent the existing publisher from making candidate media public.** The plan says to deploy the Caddy deny route and publisher rule “together,” but gives no publication freeze, deployment ordering, or readiness gate. The currently deployed `prepare_shared_media` copies candidate files into public `static/media` before `promote_candidate` (`controller/src/publisher.rs:867-881, 2035-2048`). A new Caddy tombstone route alone does not hide an untombstoned candidate. Ansible copies the Caddyfile and queues service restarts (`deploy/ansible/roles/autographs_deploy/tasks/main.yml:407-414, 550-576`), so “together” is not an atomic replacement of both processes. **Required property:** No publish can execute the old candidate-to-shared path during rollout, and the revised publisher/Caddy pair must be ready before publication resumes. **Example route:** Specify an operator publish freeze and post-deploy readiness/HTTP checks, then resume publishing.

2. **WARNING — The deployed precommit proof needs a feasible pause or failure mechanism.** Wave 8 requires observing a candidate-only URL return 404 “while promotion is deliberately paused or forced to fail,” but the existing credentialed smoke has no promotion pause/fault hook (`controller/tests/live_static_publish_smoke.rs` publishes and fetches only after completion), and the implementation step adds only a unit-test callback. **Required property:** The live acceptance gate must state a repeatable, safe way to inspect the deployed Caddy origin during the precommit interval, or explicitly make the controlled local callback plus real Caddy HTTP fixture the precommit proof and reserve the deployed smoke for postcommit behavior. **Example route:** Add a test-only pause in an isolated disposable publish environment, or revise the live gate to match the proposed deterministic tests.

3. **WARNING — The takedown operator procedure needs an explicit writeability and durability preflight.** The plan gives `sudo install` into a Podman volume after `volume inspect`, but does not require checking that the Caddy container sees the marker on its read-only mount or that the chosen host mountpoint is the same volume used by the controller/Caddy quadlets (`autographs-controller.container.j2:15`, `autographs-caddy.container.j2:14`). The subsequent origin 404 check catches failure, but the procedure calls marker creation the takedown commit before proving that serving sees it. **Required property:** The operator action must verify the exact marker is present in the mounted origin namespace before treating the URL as denied, and record both origin routes' 404 responses as the effective commit evidence. **Example route:** Include a volume identity/readback check and name the successful dual-route origin probe as completion of the origin deny step.

## Round 3 reassessment review — ISSUES FOUND

The second verdict above applied to the earlier revision. ### Blocker

**1. [deployment/publish quiescence] Every old publisher request must finish or be proven unable to enter candidate-to-shared copying before the new Caddy route is activated.**

- **Severity:** BLOCKER
- **Evidence:** `08-PR-294-CONTRACT-REVISION.md` §4.2 calls for waiting until publish status is terminal and *known* clients receive responses, then restarting the old controller “to cancel any residual accepted queue.” `controller/src/routes.rs:1953-1967` authorizes each publish request and awaits `acquire_publish_lock()` **before** setting publisher status inside `publish_locked`. Thus an accepted request may be waiting without appearing as running. Once the current holder finishes, that waiter can take the mutex and execute the old candidate-to-shared path before the restart stops it. A restart request is not a barrier on mutex acquisition or file writes. The plan's preflight checks PID/start time and an unchanged `current` target, but neither detects a candidate WebP that the old code already copied into public shared `media` while the pointer stayed unchanged. The manual Caddy gate blocks *new* ingress only; it does not stop requests already inside the old controller. The proposed fixture's “active/queued drain behavior including controller restart” cannot establish this invariant without an explicit queue boundary or a serving-level protection for the interval.
- **Required property:** Before any new Caddy route can serve shared media, no accepted old-code request can still start or continue pre-promotion candidate copying, including unknown requests queued on the mutex. The preflight must verify that property using an observable barrier, and the test must inject a queued request at the handoff to prove it.
- **Example route (non-binding):** Add a temporary old-controller publish admission/drain barrier that rejects queued requests and reports zero active/queued work, or keep candidate-only shared paths unreachable at Caddy until the old process is fully stopped and the revised controller is running. Preserve current committed media throughout.

### Checks that now pass at plan level

- **Actual workflow options:** The revised §4.1 names `.github/workflows/deploy.yml`'s `Run full deployment` action, its `directory: deploy/ansible`, `playbook: playbooks/deploy.yml`, and the exact `options` addition. The current workflow has no freeze extra var, and the role currently defaults false; the plan explicitly changes both and adds a test parsing the workflow call rather than only a render fixture.
- **Failure and retry:** §4.3 retains the managed gate and protected record across Caddy/controller restarts and faults, rejects false in full deploy, and makes retry re-enter the frozen preflight. The separate rollback path is included and remains frozen if reverting to an image without the revised media contract.
- **Readiness and unfreeze:** §4.4 adds digest/release/source verification, both origin routes, marker denial, frozen POST responses, static-current integrity, a separate host-side unfreeze playbook, authentication-only POST probes after unfreeze, restoration on failure, and a release-completion dependency on successful unfreeze. These match the workflow's existing post-deploy health and release-gate placement.
- **Operator/fixture scope:** §4.5 tests a pre-frozen host, missing/partial gate refusal, restart failures, retry, bootstrap, and distinct deploy/unfreeze invocation parameters. The `controller-rollback` path and the Caddy/Podman volume and bind-mount topology are accounted for. The queue test needs the stronger property stated above.

The review report's `convergence.status` remains unchanged. This plan review is one of the evidence paths required by its round-3 resume criteria, but it does not approve coder resumption until the blocker is addressed and independently rechecked.
