# PR 294 public media assumptions

## Shared invariants

1. Candidate media remains private until `current` changes to the validated release. After that atomic pointer change, Caddy can serve new media through `current/media` while shared storage is populated.
2. Previously published fingerprinted URLs remain fetchable for at least the documented 24-hour origin window and while retained releases reference them. Emergency takedown deliberately overrides this guarantee for exact affected URLs.
3. An emergency-removed URL stays denied at the origin even if a shared file, retained release, rollback target, or derivative cache still has its bytes. A future candidate that references the same URL fails before promotion.
4. Public dimensions match verified WebP bytes. Round 1's dimension fix is complete and must remain intact.
5. Deployment of the Caddy route and publisher is not atomic. A Caddy publish-route gate stops new ingress but does not cancel requests already waiting on the old controller's in-process mutex. Before the revised Caddy route can restart, the old controller service and process must be stopped and observed absent; Caddy must serve the current static release independently while its private admin API is unavailable. Resume publishing only after the revised controller and both Caddy origin routes are confirmed active. The production GitHub Actions invocation must preserve the freeze through the controller and Caddy restarts. A local controlled callback plus real disposable Caddy HTTP fixture proves the precommit boundary; deployed smoke proves the postcommit path without a production pause hook.

## Failure matrix

| Event | Current effect | Required behavior |
| --- | --- | --- |
| Candidate copy completes while promotion waits or fails | New URL is anonymously readable. | Candidate-only URL remains unavailable until pointer change. |
| Pointer changes before shared copy | New URL exists in `current/media`. | Caddy serves it via fallback; shared copy is retryable without reverting the committed release. |
| Normal correction, unpublish, or rollback | Cached documents can reference old URLs. | Shared/retained media bridges origin misses for the bounded window. |
| Emergency removal deletes files but misses a retained copy | Cleanup or rollback can restore the URL. | Durable exact-path deny wins over every physical copy and prevents future publication. |
| Emergency removal deletes a manifest-listed file | Release pruning fails while rereading it. | Cleanup skips intentionally denied media and still prunes the release. |
| Old publisher runs during Caddy/controller rollout | It can still expose a candidate through shared media. | Block admin publish operations until the revised publisher and Caddy routes pass readiness probes. |
| Marker is written on a different or unreadable mount | Publisher may see it while Caddy still serves the URL, or vice versa. | Confirm controller/Caddy volume identity, marker readback in Caddy, and 404 at both public and preview origin routes before declaring origin denial. |

## Revised decisions

- Move candidate-to-shared copying after the atomic pointer change. Before promotion, migrate only already-active media. Candidate files stay in the private release directory; Caddy's `current/media` fallback covers the narrow post-promotion interval.
- Use durable exact-path tombstone marker files on the shared static volume. Caddy checks for a marker before either media file lookup. The publisher refuses candidates containing a tombstoned path, never recopies such media, and allows pruning a release with intentionally removed media while unrelated missing media still fails closed.
- Provide one operator action that creates the marker before deleting shared and retained copies, then instructs exact CDN purge and origin/edge 404 verification. Marker files persist across publish, rollback, and process restart.
- During rollout, freeze publication before replacing either process, keep the active release served, validate both new Caddy routes and the revised controller, then explicitly resume publication. The operator takedown action is complete only after both origin routes return 404 for the marked URL.
- Keep normal media retention and no-routine-purge semantics. Emergency 404 is an explicit exception.

## Round 3 mandatory convergence reassessment

**Finding lineage.** Round 1 `CR-01` caused shared media retention; its local old-URL behavior is resolved. `WR-01` dimensions is resolved. Round 2 `CR-02` was a fix regression of `CR-01`; pointer-first publishing and the real Caddy fixture resolve the local boundary. `WR-02` was a sibling retention/takedown miss; marker denial and pruning are resolved locally. Round 3 `CR-03` is a sibling deployment-consumer miss in the `CR-02` family: `.github/workflows/deploy.yml` calls the production playbook without `autographs_deploy_publish_frozen`, while the role defaults that variable to `false`. The workflow therefore removes a preexisting manual gate. No further point fix starts until this assumption and implementation contract have independent review.

**Shared invariants.** The `current` pointer remains the only commit for a candidate-only URL; retained committed URLs outlive document freshness and normal rollback; marked URLs remain denied across shared/current/retained copies; decoded WebP dimensions match public metadata; and no old publisher request runs after the new shared-media Caddy route is activated. The last invariant requires a production workflow gate that survives every controller/Caddy restart and failure, not merely a manual command.

**Complete deployment consumer inventory.** The release-please-triggered `push` and `workflow_dispatch` `retry` paths enter `.github/workflows/deploy.yml`'s serialized `production` job (`release-production` and `deploy-production` concurrency) and, for `production_mutation_required=true`, invoke `dawidd6/action-ansible-playbook` with `playbook: playbooks/deploy.yml`, `directory: deploy/ansible`, SSH inventory, controller tag/digest, release/source metadata, domain/ports, Oracle/OCI variables, and **no freeze extra var**. The role default is `false`; `tasks/main.yml` copies Caddyfile, includes `tasks/publish_freeze.yml`, and later flushes controller/Caddy restart handlers. `publish_freeze.yml` uses `blockinfile state: absent` under that default. The controller quadlet and Caddy quadlet share the static volume, Caddy binds the host Caddyfile and serves both public and preview routes, and its current `After`/`Requires` on the controller may stop static serving when the controller stops; the Caddy quadlet and live unit dependency are therefore cutover consumers. Admin full/incremental publish requests enter through Caddy; `routes::publish` waits on an in-process `LocalPublisher` mutex before setting publish status, so status alone cannot count queued requests. The operator's in-place manual gate and Ansible's copied managed gate are distinct states. The workflow's `/manifest.json` and `/admin/api/health` check verifies release metadata but not freeze, media routing, or a safe unfreeze. The separate `workflow_dispatch operation=rollback`/`controller-rollback.yml` path can restore an older controller and must not silently reopen publishing. Local publisher, Caddy HTTP, Ansible render, CI, credentialed live smoke, and Wave 8 CDN probes are verification consumers, not substitutes for the production invocation test.

**Assumption audit.** The round-2 plan assumed an operator would pass `autographs_deploy_publish_frozen=true` to Ansible. Normal Release-PR deployment passes no such parameter, so the default clears the gate. The first round-3 revision then assumed terminal `/admin/api/publish/status`, known client responses, and a later restart proved all work drained. They do not: an unknown accepted request can acquire the mutex and copy candidate media before the restart. A restart request is not a process-exit barrier. The production workflow must set or verify a freeze before Caddy/controller mutation, make Caddy independent of the controller for static serving, **stop and observe the old controller process absent before the revised Caddy route can restart**, and keep a durable frozen state. Process exit prevents further old writes but does not retract candidate-only bytes the old process already copied into shared media. The entire shared namespace, not only files added during shutdown, must be checked against evidence of committed publication; unproven paths are quarantined outside Caddy roots. A fresh URL with ambiguous provenance blocks cutover until the operator can establish its committed history or handle it as an explicit privacy exception without silently breaking normal 24-hour retention. A failed deploy remains frozen with public static serving and admin API unavailable until safe recovery. Only an explicit readiness-backed step may remove the gate. Repository-only releases do not mutate the runtime; fresh VM bootstrap has no old publisher but starts frozen until readiness passes.

**Revised decision.** The normal full-deploy role defaults to frozen and refuses an unfrozen production cutover. Before a Release PR is merged on an existing VM, the operator installs the documented manual Caddy gate; this is admission control, not queue-drain proof. A workflow preflight verifies the gate, changes the live Caddy quadlet so static serving has no controller `After`/`Wants`/`Requires` dependency, validates current public/static routes, then stops the old controller. It waits for `autographs-controller.service` to be inactive, its old main PID to have exited, and the old container to be stopped/absent before it allows any new Caddy route deployment. This process-exit barrier cancels unknown queued requests without counting them. It then audits **all** shared media against committed-release manifests/history, not just paths newly copied during shutdown; candidate-only or otherwise unproven paths move to a protected directory outside the served static root, and ambiguous fresh committed URLs block cutover until resolved. If Caddy cannot serve current static content with controller down, it aborts before new route deployment and recovers under the frozen old configuration. A newly provisioned VM has no old publisher and starts frozen. The workflow explicitly passes the frozen setting to the exact Ansible deploy call and does not invoke unfreeze on any failed path. A separate readiness-checked unfreeze action removes only the gate after controller and both Caddy routes pass. A controller-only rollback to an image without this media contract is refused while the shared-media Caddy route is active; a Caddy publish gate alone cannot make that old image safe. Tests must inject a queued request at handoff, prove no old process/write survives the barrier, and seed a candidate-only shared file **before** shutdown to prove quarantine, plus cover manual-gate preservation, both restart boundaries, failure preservation, and explicit unfreeze.

Official Caddy documentation supports a named `file` matcher with an independent `root` to test whether a marker exists at the requested path; use a `route` block to make denial precede file lookup: [request matcher docs](https://caddyserver.com/docs/caddyfile/matchers#file), [try_files docs](https://caddyserver.com/docs/caddyfile/directives/try_files). Validate with an actual Caddy process when available; source assertions alone are insufficient for Wave 8.

## Alternatives considered

Retiring every affected retained release can remove old copies, but it sacrifices rollback targets and does not prevent the same fingerprinted URL from being generated again. Tombstones provide a durable serving and publishing rule without relying on every retained copy being found manually.
